Renderers

The part that decides whether it starts

Minecraft: Java Edition asks for desktop OpenGL. Your phone speaks OpenGL ES, or Vulkan, or both. Something has to translate — and picking the wrong translator is the most common reason a version refuses to launch.

TL;DR Aerix ships eleven renderers, chooses one automatically from the Minecraft version you are launching, and lets you override that choice per instance.

The lineup

What ships in the APK

Every library below is bundled for all four Android ABIs — armeabi-v7a, arm64-v8a, x86 and x86_64.

"From source" means the library is compiled from vendored source in this repository for every ABI, rather than shipped as a binary blob. The rest are bundled unmodified from their upstream projects, with their licences preserved in the APK.

The split

Why there are two LTW renderers

This follows Minecraft's own OpenGL change, not a version number somebody picked.

Minecraft 1.8 – 1.16.5

These versions drive OpenGL 1.x / 2.1. They use fixed-function state — glAlphaFunc, glShadeModel, the matrix stack — and the legacy client-array draw path.

LTW Legacy implements exactly that pipeline.

Minecraft 1.17 and newer

1.17 moved the game to the OpenGL 3.2 core profile, which removed every one of those fixed-function calls.

LTW implements the core profile.

Neither can stand in for the other LTW has no fixed-function emulation at all, so it cannot start 1.16.5. LTW Legacy is not needed once the game is on the core profile. GL4ES covers the same ground as LTW Legacy — that is expected, both are GL 1.x/2.1 translators — and stays selectable as a fallback for devices where the newer upstream revision regresses.

Selection

How Aerix picks one

Every renderer declares its own compatibility range. Nothing in the picker hardcodes a version boundary, so a renderer cannot drift out of sync with its own compatibility window.

Your explicit choice wins

If you set a renderer on an instance, that is what runs — as long as it is loaded and it declares support for the version you are launching. An override the version does not support is rejected up front, instead of being honoured and then failing the launcher's own compatibility check seconds later.

Otherwise the version decides

1.16.5 and older falls through LTW Legacy → vgpu → vgpu 1.3.6β → GL4ES → VirGL, best first. 1.17 and newer falls through LTW → MobileGlues → Zink.

If nothing matches, it says so

Rather than refusing to launch, Aerix uses the first loaded renderer and records the choice and the reason in the launch log. A surprising pick can always be traced back to a line explaining it.

Provenance

Why "built from source" matters

Before this, the legacy renderer path depended on a prebuilt GL4ES binary with no source in the tree. It could not be audited, patched, rebuilt for a new ABI, or updated — and it silently drifted from the NDK and the platform it linked against.

LTW Legacy

Built from a vendored snapshot of GL4ES, pinned to an exact upstream commit and version. Aerix supplies its own CMake project, drops upstream's optional EGL wrapper so it never competes for eglGetProcAddress, and renames the output so it can coexist with the other GL4ES builds.

GL4ES is MIT licensed. The upstream licence and copyright notices are preserved.

Checked on every build

A verifier runs against every APK the CI produces. It opens the archive, confirms libltw.so, libltwlegacy.so, libvgpu.so and libvgpu_1368.so are present for the requested ABI, and checks each one is a genuine ELF shared object of the right class and machine.

A missing or wrong-architecture renderer would otherwise stay invisible until somebody launched the matching Minecraft version on a real phone.
